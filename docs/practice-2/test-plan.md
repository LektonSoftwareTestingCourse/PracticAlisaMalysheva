# План тестирования СМП

## 1. Назначение и область

План описывает порядок проверки СМП, критерии начала и завершения, ресурсы, расписание, риски и метрики.
Область совпадает с тестовой стратегией: полный тест-дизайн ядра (Authorization и Card-Management), smoke-тесты
и проверки критического пути для периферийных сервисов.

**Порядок работ:**

1. готовность окружения
2. smoke всей системы
3. тесты ядра с приоритетом P0
4. интеграционный тест - критический путь
5. периферийные сервисы P1/P2/P3
6. повторный прогон затронутых проверок после изменений

## 2. Критерии входа

- Требования к Authorization и Card-Management, архитектура и API-контракты доступны и приняты как тестовый базис.
- Docker Compose поднимает все сервисы, PostgreSQL и RabbitMQ; health-check обязательных сервисов успешен.
- Состояние БД перед кейсом известно и воспроизводимо.
- Обе PICT-модели разбираются, наборы сгенерированы и содержат корректные строки.
- Сгенерировано не менее 20 тестовых карт; доступны карты с нужными статусами, лимитами и балансом.

## 3. Критерии выхода

- 100% обязательных артефактов сданы по путям из заданий каждого этапа.
- 100% классов эквивалентности и троек граничных значений ядра связаны хотя бы с одним тест-кейсом.
- Все строки PICT-наборов спроецированы в отдельные тест-кейсы.
- Выполнены 100% smoke-тестов и критических пунктов из чек-листа (приоритета P0).
- Пройдены успешно не менее 95% всех запланированных проверок, при необходимости зафиксированы причины неуспешного
  прохождения.
- Отсутствуют открытые дефекты критического и высокого уровней.
- Результаты воспроизводимы и стабильны.

## 4. Приостановка и возобновление

**Приостановка.** Проверки останавливаются, если окружение неработоспособно (не поднимается Gateway или сервис ядра,
недоступны PostgreSQL/RabbitMQ), если нельзя подготовить управляемые тестовые данные, если ответы API массово расходятся
с контрактом, либо если зафиксировано нарушение денежной целостности - в этом случае результаты дальнейших проверок
недостоверны.

**Возобновление.** Работа продолжается после устранения причины, успешного health-check затронутых сервисов и возврата
БД
к известному состоянию. Обязательный шаг - повторный smoke-прогон. Для исправленного дефекта сначала перезапускается его
кейс,
затем связанные проверки P0 и P1, чтобы убедиться в отсутствии регрессий.

## 7. Риски

| Риск                                                   | Влияние                                               | Снижение                                                                                                      |
|--------------------------------------------------------|-------------------------------------------------------|---------------------------------------------------------------------------------------------------------------|
| Конфликты между ТЗ, OpenAPI и реализацией              | Невозможно зафиксировать ожидаемый результат          | Каждый кейс привязан к конкретному требованию; спорные места выносятся на уточнение до прогона                |
| Случайные данные симуляторов и генератора карт         | Невоспроизводимость результатов                       | Для ядра готовятся явные фикстуры; случайные значения используются как неуправляемые факторы                  |
| Накопление значений баланса и лимитов между сценариями | Ложные результаты последующих проверок                | Изоляция фикстур по картам; откат состояния перед/после прогона кейса                                         |
| Асинхронная доставка через RabbitMQ                    | Проверка конечного состояния раньше обработки события | Ожидание с ограничением по времени; проверка состояния в Logger и Notification Service, а не факта публикации |
| Неатомарность проверки баланса и резервирования суммы  | Возможны гонки данных при параллельной нагрузке       | В функциональном наборе - последовательный запуск; конкурентный сценарий - отдельный нагрузочный тест         |
| Изменение PICT-модели после генерации набора           | Устаревший маппинг строк на тест-кейсы                | После правки модели набор пересобирается целиком, маппинг проверяется заново                                  |
| Недоступность Bin Lookup во время прогона              | Ложные падения интеграционных сценариев               | Принят graceful degradation; fallback на issuerId от Switch явно указан в ожидаемых результатах               |

## 8. Метрики

- Покрытие требований процессингового ядра тест-кейсами.
- Покрытие классов эквивалентности и граничных точек.
- Доля строк PICT-наборов, спроецированных в отдельные кейсы - целевое значение 100%.
- Соотношение выполненных, пройденных, непройденных и заблокированных проверок.
- Процент прохождения по приоритетам P0/P1/P2/P3.
- Число открытых дефектов в разрезе критичности.
- Доля пройденных пунктов smoke и критического пути.
- Воспроизводимость: количество тестов, изменивших результат при повторном прогоне без правок системы.
