## 2. Бизнес-отказы

Каждый исход проверяется совместно — и доменный код (`responseCode`), и причина
(`declineReason`). Часть исходов имеет совпадающие коды (05 у BLOCKED/INACTIVE),
поэтому проверка только кода их не различает — проверяется и причина.

| Исход                | Код | Причина              | Путь достижения                                  | Способ подготовки данных                          | Статус |
|----------------------|-----|----------------------|--------------------------------------------------|---------------------------------------------------|--------|
| CARD_NOT_FOUND       | 14  | CARD_NOT_FOUND       | по данным запроса (валидный PAN, карты нет)      | PAN = bin + 10 случайных цифр                     | ✅      |
| UNKNOWN_BIN          | 14  | CARD_NOT_FOUND       | по данным запроса (BIN не маршрутизируется)      | PAN с BIN 999999                                  | ✅      |
| INSUFFICIENT_FUNDS   | 51  | INSUFFICIENT_FUNDS   | состояние карты (остаток мал)                    | карта `initialBalance=100`, сумма 1000            | ✅      |
| CARD_BLOCKED         | 05  | CARD_BLOCKED         | состояние карты                                  | PATCH статус BLOCKED                              | ✅      |
| CARD_INACTIVE        | 05  | CARD_INACTIVE        | состояние карты                                  | PATCH статус INACTIVE                             | ✅      |
| CARD_EXPIRED         | 54  | CARD_EXPIRED         | состояние карты                                  | PATCH статус EXPIRED                              | ✅      |
| EXCEEDS_AMOUNT_LIMIT | 61  | EXCEEDS_AMOUNT_LIMIT | состояние карты (лимит) + данные запроса (сумма) | карта `dailyLimit=100`, остаток 100000, сумма 500 | ✅      |

Различие путей: исход, достижимый состоянием карты (BLOCKED/INACTIVE/EXPIRED/
INSUFFICIENT_FUNDS) и достижимый данными запроса (CARD_NOT_FOUND — несуществующая
карта, EXCEEDS_AMOUNT_LIMIT — сумма между остатком и лимитом, UNKNOWN_BIN — неверный
BIN). Оба пути проверены (см. `TransactionsApiTest`, `AuthorizationInternalApiTest`).

Один и тот же исход проверяется двумя способами: через Gateway (`POST /api/transactions`,
все отказы — HTTP 200, исход в теле) и через внутренний эндпоинт
`POST /api/internal/authorize` (маппинг исхода в HTTP-статус: 403/404/422/400).

## 4. Расхождения контракта и реализации

(см. раздел 7), поэтому классификация — по анализу кода.

## 5. Обоснование достаточности

Выделенные классы входных данных:

- **Карты:** валидная/несуществующая (CARD_NOT_FOUND), по состоянию (ACTIVE/BLOCKED/
  INACTIVE/EXPIRED/DELETED), по остатку (достаточно/недостаточно средств), по лимитам
  (в пределах/превышение дневного лимита), по BIN (известный/неизвестный).
- **Транзакции:** одобренные, отклонённые по каждому исходу, повторная доставка
  (новая/та же/конфликт ключа), асинхронное сохранение.
- **Валидация:** длина/формат строк, числовые ограничения, обязательность, enum-значения
  — с классами эквивалентности и границами.
- **Поиск/фильтры:** каждый фильтр (`pan`, `status`, `limit`, `offset`, `dateFrom/dateTo`),
  пустая выборка, некорректные комбинации.

Полнота подтверждена: перечень эндпоинтов построен по трём источникам; для каждого
эндпоинта покрыты статус-коды из контроллеров и `@ApiResponse`; каждый исход авторизации
покрыт по двум путям (Gateway и внутренний). Приёмы из задания (RequestSpecification,
`@ParameterizedTest`, GPath-фильтр, `matchesJsonSchemaInClasspath`, проверка заголовков,
Awaitility с явными границами, композитные матчеры, проверка тела для 2xx и 4xx)
продемонстрированы в коде.

Осознанно оставлено вне покрытия:

- **`POST /api/cards` → 409** (дубликат PAN): PAN генерируется сервисом, коллизию через
  публичный API не воспроизвести без прямого доступа к БД, что запрещено приёмом
  «изоляция через API». Отмечено как ограничение.
- **`503` для Gateway/авторизации при недоступности downstream** (`SERVICE_UNAVAILABLE`,
  `RESERVATION_FAILED`): требует остановки сервиса/брокера, что дестабилизирует общий
  стенд и делает прогон невоспроизводимым. Поведение кода зафиксировано в `DeclineOutcome`,
  но проверка требует изолированного стенда (вне объёма одной команды).
- **Симуляторы (мерчант/терминал)** покрыты минимально (структура ответа и валидация),
  без нагрузочных сценариев — они относятся к практике 6.
- **WebSocket `/ws/transactions`** не покрыт: область практики 5 ограничена синхронными
  HTTP-контрактами.

## 6. Доказательства работоспособности проверок

Модуль скомпилирован (`mvn -P api-tests test-compile`, JDK 21) — все 12 тестовых
классов и support-слой компилируются. Запуск прогона требует поднятого стека
(docker), который в текущей среде недоступен; три последовательных зелёных прогона
и «красные» проверки ниже выполняются в CI (`practice-run.yml`, практика 5) при сдаче.

Ниже — три запланированных эксперимента намеренной поломки (мутации) и ожидаемый
результат:

| Тест                                                   | Внесённое изменение                                                                                   | Ожидаемый результат                                                                         |
|--------------------------------------------------------|-------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------|
| `authorize_approvedCard_returns200_approved`           | Ожидание `responseCode` изменить с `"00"` на `"99"`                                                   | Тест краснеет: `expect responseCode to be "99"` при фактическом `"00"`                      |
| `CardsValidationApiTest.createCard invalid cardholder` | Убрать проверку `message containsString("uppercase")`                                                 | Не падает на теле — подтверждает важность проверки тела, а не только статуса                |

| Мутационная проверка идемпотентности                   | В `IdempotencyApiTest` отключить дедупликацию (изменить ожидание повторной доставки с `200` на `201`) | Тест краснеет, пока дедупликация активна; подтверждает, что проверка реально ловит дубликат |

## 7. Порядок запуска

Одна команда (стека нет — сначала поднять):

```bash
cp .env.example .env
make run          # docker compose up -d
make api-test     # mvn -f services/pom.xml -P api-tests test
```

Эквивалент без Makefile:

```bash
docker compose up -d
mvn -f services/pom.xml -P api-tests test
```

CI: `practice-run.yml` → workflow_dispatch → `practice=5` — поднимает стек и
запускает `mvn -f services/pom.xml -P api-tests test`.

Адреса сервисов переопределяются переменными окружения (`GATEWAY_URL`,
`CARD_MGMT_URL`, `AUTH_URL`, `LOGGER_URL`, `SWITCH_URL`, `NOTIFICATION_URL`),
по умолчанию — порты локального стека.

> Примечание о верификации: в среде разработки docker недоступен, поэтому
> рантайм-прогон и «красные» проверки выполняются в CI при сдаче. Компиляция
> модуля подтверждена. Ожидания тестов выведены из кода контроллеров, DTO и
> спецификации (ссылки на источники указаны в комментариях и в разделах выше).
