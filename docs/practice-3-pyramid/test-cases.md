# Практика 3. Тест-кейсы по уровням пирамиды

## 1. Новые тест-кейсы (часть «б»)

### Правило выбора уровня

Уровень определяется по тому, где живёт находится проверяемая логика, а не по способу исполнения теста (практика 2
затрагивала в основном HTTP-контракт, но многие кейсы проверяют логику, лежащую в одном классе).

| Где находится логика, проверяемая в сценарии                                      | Уровень     | Пример                                                                        |
|-----------------------------------------------------------------------------------|-------------|-------------------------------------------------------------------------------|
| в одном классе или методе, зависимости подменяются без потери смысла              | unit        | `AuthServiceImpl`, `RoutingService`, `Card.startReservation`, `LuhnValidator` |
| в HTTP-контракте одного сервиса: статус-код, тело ответа, валидация и маппинг     | api         | reason -> HTTP-код, `GlobalExceptionHandler` 404/402/409, фильтр Gateway      |
| в SQL, транзакциях, брокере сообщений - то что не замокать                        | integration | `upsertLimitUsage`, `FOR UPDATE`, `@SQLRestriction`, Criteria API, RabbitMQ   |
| только в полной цепочке с Gateway, Logger/Notification, пользовательский сценарий | e2e         | жизненный цикл карты глазами клиента                                          |

Итого: 26 (unit 13 / api 6 / integration 5 / e2e 2). Покрыты оба пути:

- **sync** - валидация (API-02), маршрутизация по BIN (API-01), лимиты/баланс (UNIT-02/03/07/10),
  CRUD и смена статуса (API-03), отказ после блокировки (API-04), резервирование (API-05, API-06);
- **async** - доставка в Logger (INT-01), publisher-confirm + reversal (INT-02), outbox -> Notification (INT-03), DLQ (
  INT-04), retry outbox (INT-05).

## 2. Распределение тест-кейсов практики 2 (часть «в»)

Исходные кейсы: `docs/practice-2/test-design.md` (ветка `practice-2`), 115 кейсов.
Уровень определён по правилу §0: **где живёт проверяемая логика**. Поэтому кейсы, проверяющие бизнес-правило
в одном классе (порядок проверок, границы, DTO-валидация), отнесены к **unit**, даже если практика 2 выполняла их
через HTTP; кейсы, смысл которых в SQL/брокере, - к **integration**; контрактные маппинги ошибок - к **api**.

### 3.2 Почему пирамида такая

1. **Основание (unit) - 56%** По правилу к unit отнесено всё, где проверяемая логика живёт в одном классе:
   ветвления и порядок проверок в `AuthServiceImpl` (включая pairwise AUTH-PW), сравнение баланса, границы срока,
   DTO-валидация (`@Bin`/`@Pan`), генерация PAN и расчёт количества в `CardGeneratorService`. Это реальная бизнес-
   логика, но по месту обитания логики это unit.

2. **Средний слой (api + integration) - 42,6%**
    - *api (14,2%)* - только контрактные маппинги: reason -> HTTP-код, 404/402/409/400 в CMS, классификация сетевых
      ошибок. Маппинги одного сервиса, полная цепочка не нужна.
    - *integration (28,4%)* - логика, которой в Java нет: native SQL лимитов (`upsertLimitUsage`), конкурентность
      (`FOR UPDATE`), скрытие DELETED (`@SQLRestriction`), пагинация (Criteria API), списание баланса (резерв в БД
      CMS), асинхронная доставка в Logger и outbox -> Notification.

3. **E2E - 1,4% (2 кейса)** Сквозная цепочка поднимает 9 контейнеров и зависит от eventual consistency; оставлены
   только сквозные сценарии, важные для пользователя (happy path и declined через эмулятор терминала).

### 3.3 Риски и порядок автоматизации

| Приоритет | Что автоматизировать                                                                     | Уровень     | Почему                                                       |
|:---------:|------------------------------------------------------------------------------------------|-------------|--------------------------------------------------------------|
|     1     | Порядок проверок авторизации (AUTH-PW/MAN), DTO-валидация, PAN/срок/баланс, outbox retry | unit        | Дёшево, ловят логические ошибки раньше; самая большая группа |
|     2     | Лимиты в SQL, пагинация, скрытие DELETED, списание баланса                               | integration | Логика живёт в БД; мок проверял бы сам себя                  |

|     4     | Happy path, declined (BLOCKED)                                                           | e2e         | Дорогие; держать набор малым                                 |
